# Docs

Architecture and implementation details that are too specific for CLAUDE.md.

## Architecture (current state)
Worldgen plus a first client-side light renderer (see below). There is no networking or tests yet.

- `StoryAmyCoreMod` (main entrypoint) defines stories in Java: `StoryEngine.addStory(...)`, then `story.AddFirstChapter(...)`. `StoryAmyCoreClient` and `StoryAmyCoreModDataGenerator` are empty.
- `core/`: `Story` (name, modId, chapters map, overall `Zone`), `Chapter` (size, landscape/environment structures, allowed biomes, base Y, placement data), `StoryEngine` (static global state + coordinate bit-packing like `XandZAsLong`), `Zone`, `BlockPos2D`, `IChunkChapters` (mixed into `Chunk`).
- `nbt/`: `ServerDataManager` reads/writes `<world>/story_data.dat`. Only each story's `storyArea` and each chapter's `ringArea`/`chapterArea` are persisted, as packed longs.
- `item/`: one creative tab (`ModItemGroups`); `ModItems` holds the story book and story compass.
- `mixin/WorldgenerationPipeline/`: the flow is
  `MinecraftServerMixin` (load data + structure templates at init, save on shutdown) →
  `ServerWorldMixin` (first Overworld load: randomize placement) →
  `ChunkChapterFilterMixin` (at `populateNoise`, tag chunks overlapping a chapter's ring) →
  `CarverMixin` (cancel caves in chapter chunks) →
  `SurfaceBuilderMixin` (calls `StoryEngine.stampChapters`: stamp landscape, blend rings toward vanilla height, place environment, update heightmaps).
  Flat worlds skip the noise generator, so `FlatChunkGeneratorMixin` calls the same `stampChapters` after the layers are placed (and rebuilds the heightmaps) and `FixedBiomeSourceMixin` is the flat counterpart of `ChapterBiomeMixin`.
  `ChunkMixin` implements `IChunkChapters`.
  `FeaturesMixin` skips placed-feature positions in the no-features mask (see below); `LakeFeatureMixin` blocks lava lakes inside rings.
- Chapter generation toggle: `StoryEngine.chapterGenEnabled` (persisted per world in `story_data.dat` as `chapterGen`, missing key = true). `ServerWorldMixin` skips placement when it is false. New worlds take `StoryEngine.newWorldChapterGen`, set by the "Chapter Generation" button that `mixin/CreateWorld/MoreTabMixin` (client) adds to the More tab of the create world screen; the button turns itself off when a debug world is selected and restores the previous choice when leaving it. `ServerDataManager` consumes `newWorldChapterGen` when there is no `story_data.dat`.
- Landscape/environment are `.chap` files (see "Chapter file format" below) in `src/main/resources/data/<modId>/chapters/`, loaded by `Identifier(modId, name)`.
- Both are read by `ChapReader` into the chapter's internal tiles (`LandscapeTile`): the landscape into column maps, the environment into per-tile block maps (`Chapter.getEnvironmentState`).
- Big landscapes can be split into internal tiles with the optional chapter field `landscapeTileSize` (`{"x": 125, "z": 125}`): it must divide `size` evenly. The landscape is always one file, `<landscapeName>.chap`, and `populateLandscapeMap` reads it once through `ChapReader`, handing each vertical span to the tile that owns its column, so the block list is never in memory, only the per-tile column maps. Only the top solid block and the water of each column are used, so the file can be lean (the engine fills below the surface itself). Every tile is a `LandscapeTile` with its own world area and its own column map; `Chapter.getLandscapeY(x, z)` finds the tile by integer division and only then does one hash lookup in that tile's map. Without the field the chapter is a single tile covering the whole size. All tiles of a chapter share one Y origin. `baseElevation` from the JSON is only used for the biome check at placement; once the chapter is placed, the Y origin is the generator's ground height at the chapter's center minus one (`ServerWorldMixin`), saved as `baseHeight` in the chapter's NBT, so the landscape sits on the terrain on flat and noise worlds alike. Each tile also keeps the template's solid surface block per column (`getLandscapeSurface`) and the water level where water lies above it (`getWaterY`), so stamping uses the template's grass, stone, sand and gravel and fills rivers and lakes instead of using the world's top block.
- Chapters are added with `StoryAmyApi.addFirstChapter` / `addChapter(modId, storyName, chapterName, ChapterCreateInfo)`. `ChapterCreateInfo` (`core/`) is a plain struct: set the required fields (`sizeX`, `sizeZ`, `landscapeName`, `landscapeBlockState`, `environmentName`, `allowedBiomes`, and `offsetFromPrevious` for every chapter but the first) and only the optional ones the chapter needs (`forbiddenLandscapeBlocks`, `baseElevation`, `landscapeTileSize`, `biome`, `minBiomeShare`, `litterGrass`, `ringRadius`, `adaptiveRing`, `steepnessAdaptationFactor`); unset optional fields keep their defaults and are not written to the JSON. Invalid values fail at registration. The long overloads with every value as an argument still exist for older callers and just build a `ChapterCreateInfo`. The values are still only written to `Stories/` when the chapter entry is missing.
- `ringRadius` (optional chapter field, default `StoryEngine.ringRadius` = 64): how many blocks the blend ring around the landscape spans. The terrain height goes from the landscape edge to the vanilla height over that many ring layers, so a bigger value gives a more gradual slope (each layer is about one block of height change) for chapters whose edge differs a lot from the terrain. The ring area is saved at placement, so a changed value only applies to chapters placed afterwards (new world).
- `adaptiveRing` + `steepnessAdaptationFactor` (optional chapter fields, off by default): with `adaptiveRing` true the ring may grow beyond `ringRadius` where the vanilla terrain around the chapter is far from the landscape's edge height. At placement (`Chapter.extendRingForSteepness`, called from `ServerWorldMixin` right after the landscape map is built) the generator's height is sampled on an 8-block grid inside the ring; the largest difference times `steepnessAdaptationFactor` (ring blocks per block of height difference) is the radius needed. The ring only grows: never below `ringRadius`, never above `Chapter.MAX_ADAPTIVE_RING_RADIUS` (256). The difference is only measured inside the current ring, so it is an estimate. The final radius is not stored separately: `Chapter.LoadFromNbt` derives it from the saved `ringArea` and `chapterArea`. The story area grows with the ring; a later chapter's placement is not re-checked against it.
- Placement is random, drawn from a `Random` seeded by the world seed and the story key (same seed, same positions), with up to 100 retries and a growing radius until the 4 corners and center are in allowed biomes; otherwise it throws. Ring layers are computed by BFS from the landscape border. Coordinate data uses fastutil maps.

## Chapter block (streaming structure block)
The vanilla structure block, patched by `mixin/StructureBlock/*`: no 48-block limit (`readNbt` and the update packet, which appends the real offset/size as var ints, so client and server both need the mod) and save/load are streamed. Save: `StructureStreamSaveJob` scans the region a slice per tick and writes it through `ChapWriter` one 32x32-column region at a time (air and structure voids are skipped, entities are not saved). Load: `StructureStreamLoadJob` reads the file through `ChapReader` on a background thread and places spans a slice per tick (`StructureStreamJobs`, 25 ms budget). The chapter block saves to the mod project's own `src/main/resources/data/<ns>/chapters/` when run from the project (dev environment), so the normal build packs it into the jar; outside dev it saves to `<world>/generated/<ns>/chapters/`. Loading reads that saved file first, then the mods' and data packs' `chapters/` (`StructureStreamJobs.chapterPath` / `open`).

## No-features mask

- Optional structure template named after the chapter's environment: `<name>-environment` becomes `<name>-no-features` (a name without the `-environment` suffix gets `-no-features` appended). Without the file the chapter has no mask.
- It lives in `src/main/resources/data/<modId>/chapters/` of the mod that registers the story, beside the environment and must have the same X/Z size. A mismatch logs an error and throws at load. Y may differ.
- It is placed at the same origin as the environment, so columns map 1:1.
- Every block in it masks its x/z column from every feature (trees, rocks, patches, ores), whatever its type, except red wool. Red wool only pins the template's corners so its size matches the environment.
- `Chapter.populateEnvironmentMap` fills `Chapter.noFeaturesMask`. `FeaturesMixin` filters `PlacedFeature` positions through `StoryEngine.isInNoFeaturesMask`.
- The check tests the origin and the columns up to `StoryEngine.NO_FEATURES_MARGIN` (4) blocks around it, so a tree crown or rock blob rooted just outside does not reach in. Larger features can still overhang.
- `litterGrass` (optional chapter field, default false): true lets ground cover (features of type random patch or flower: grass, ferns, flowers, mushrooms, pumpkins) be scattered inside the mask as well; false masks them like everything else.

## Light renderer (client only)

- Package `render/`, started from `StoryAmyCoreClient` via `LightManager.init()`. Never referenced from common code.
- `Light` (cookie texture, intensity, fov, `viewToLight`), `ILightBackend`, `LightManager` (light list + backend choice: Sodium loaded → `SodiumLightBackend`, else `VanillaLightBackend`).
- `CookieLightPass` draws one fullscreen quad at `WorldRenderEvents.AFTER_TRANSLUCENT`: it reads the main framebuffer depth, rebuilds view-space position, projects it into the light and adds the cookie texture (additive blend). Shader: `assets/minecraft/shaders/core/storyamycore_cookie_light.*` (vanilla `ShaderProgram` only loads from the `minecraft` namespace), reloaded with resources (F3+T).
- `SodiumLightBackend` currently extends the vanilla one unchanged; it is the seam for Sodium-specific injection. Sodium is `modCompileOnly` (Modrinth maven).
- The flashlight is no longer built in: it lives in the SlenderMan's Arrival: Revisited mod, which registers it through `StoryAmyClientApi` like any other mod. It is the reference user of `Light.updater`, `affectItem` and the far/near beam values.

## Client render API (client only)

`api/StoryAmyClientApi` is the only class other mods should use. Everything is keyed by `(modId, id)`; duplicates and unknown ids throw. Render/client thread only, client-only, no networking.

- Lights: `registerLight/getLight/setLightEnabled/removeLight`. A `Light` has `modId`, `id`, `enabled`, all the attribute fields, and an optional `updater` (`BiConsumer<Light, WorldRenderContext>`) called every frame before drawing, also while disabled. Don't register or remove lights from inside an updater.
- World shaders: `registerWorldShader/setWorldShaderEnabled` with an `IWorldShader` (`reload`, `render`). Runs in `LightManager`'s `AFTER_TRANSLUCENT` hook right after the lights, with the same depth/normal/albedo buffers.
- Receivers-only lights: a `Light` with `affectEntities/affectEntity`, `affectItems/affectItem` or `affectBlockEntities/affectBlockEntity` (usually with `point = true`) lights only the models those predicates match (terrain blocks are not supported). `LightManager.receivesEntity/receivesItem/receivesBlockEntity` are asked while each model is drawn; a match is drawn a second time by `ReceiverMask` with a copy of each render layer that uses `storyamycore_receiver_mask` (writes normal, albedo and the mask in `NormalBuffer` attachment 3, nothing visible). The hooks are `EntityRenderDispatcherMixin`, `ItemRendererMixin` (not the GUI) and `BlockEntityRenderDispatcherMixin`. The cookie shader discards pixels whose depth differs from the mask. The first-person hand is drawn after the world, so `GameRendererMixin` runs a second light pass (`LightManager.renderHand`, receivers-only lights, hand projection) after `renderHand`. Limits: every receivers-only light lights all marked models, not only its own; only layers in the entity vertex format are marked; a receiver is drawn twice. The flashlight's tip light in SlenderMan's Arrival: Revisited uses it for the flashlight item.
- Entity shaders: `EntityShaderManager`. `EntityRenderDispatcherMixin` wraps the `VertexConsumerProvider` passed to `EntityRenderer.render`; the first enabled rule whose predicate matches swaps every `RenderLayer` the entity requests for a copy with only the shader program replaced (rebuilt through the `RenderLayer$MultiPhaseParameters` entries in `noiseaccess.accesswidener`, cached per rule and layer). Programs come from Fabric's `CoreShaderRegistrationCallback` (own namespace). `receivesLights` adds the program name to `NormalBuffer.SHADERS`; the shader must then write `normalOut`/`albedoOut`. Limits: a uniform is shared by the whole batch of entities drawn with the same layer, not set per entity; layers that are not `MultiPhase` are left alone; the wrapper is not a `VertexConsumerProvider.Immediate`.
- Post effects: `PostEffectManager`. A mod ships a vanilla-format post effect json (`assets/<modid>/shaders/post/<name>.json`) plus its shaders; `GameRendererMixin` runs the enabled effects in registration order right before `GameRenderer.render` rebinds the main framebuffer for the HUD (after vanilla's own post processor). Processors are created when first enabled, rebuilt after a resource reload and resized with the window. `setPostUniform` sets a float uniform in every pass that declares it (reapplied each frame).
- Shared helpers: `render/RenderRegistry` (`key`, `fail`).


## Chapter file format (`.chap`)
Layout is documented in `core/ChapFormat.java`. A file is a header (magic, version, size, DataVersion, region size), one independently deflated block per 32x32-column region, and a footer (palette, region index, footer offset). A region stores, per column, vertical spans (gap, length, palette index) of one block state; block entities of the region follow as NBT blobs (the only NBT left). Block states are stored as id plus property strings. There is no datafixer: a changed block id or property fails loudly on load. `ChapWriter` and `ChapReader` are the only code that touches the format.
